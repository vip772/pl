# 消息菜单扩展（第一阶段：实机诊断）

## 最终规格

- 同一个 Provider 同时出现在“增强”和“新功能”。
- 只有一个总开关，默认关闭，不提供数量编辑项。
- 最终开启布局：每排 6 个，按原顺序自动换行，最多 5 排（30 个）。行数按实际项目数量使用，不填充空项目。
- 最终关闭布局：交还微信原生实现，原生为每排 5 个、最多 3 排。
- 超过 30 个项目的处理尚未实现，不擅自修改原始菜单模型或点击索引。

## 本次交付边界

**这是功能入口和定向诊断版，不是已实现 6×5 的功能版。**

当前开启只输出诊断，菜单布局、菜单项绑定、点击分发和弹窗定位均不修改。设置页明确展示该限制。关闭不记录菜单调用和结构诊断，安装阶段仍可记录定位结果。

依据用户提供的微信 8.0.78 逆向摘要，只观察 `eu5.s0.p(int,int)` 与 `eu5.l0`，版本名称不是 8.0.78、类或方法不匹配时失败关闭，不猜其他版本入口。版本代码记录进日志，但未声称覆盖所有 8.0.78 APK 变体。缺少其它 APK，因此未进行横向验证。

原生三排的容量限制发生在 View 挂入界面之前。仅重排现有 View 无法确保恢复第 16 项及以后项目；缺少完整方法与回调证据时，不替换方法，不手工调用未知构造或回调。

## 初版诊断内容（以下高负载诊断已在减负修订中删除）

日志前缀：`[Hchat:消息菜单扩展诊断]`。

- `settingsSave`：开关保存结果。
- `install` / `locate` / `versionGate`：微信版本、完整方法签名和定位结果。
- `itemSignatures`：真实构造及方法签名。
- `showEnter` / `showExit`：每次调用独立 session，不采用只记录前 40 次的策略。
- `menu.before` / `menu.after`：字段类型、集合长度、弹窗宽高、View 层级与布局测量状态。
- `itemCreate` / `itemField`：原生项目构造参数类型、其持有 View 与原生索引参数。
- `itemViewCallback`：已构造项目实际触发的单 View 参数方法签名；未假设这些方法都是点击方法。
- `nextFrame`：项目附着与挂入状态。

单次快照最多读取 60 个字段、100 个 View 节点、10 层；项目字段最多 20 个。弱引用追踪，仅观察当前 show 调用内的项目构造，不 Hook Android 全局 PopupWindow/addView，不持久保存菜单对象。不读取 TextView 文本、菜单标题、消息正文或业务对象 toString。

## 实机测试

1. GitHub 构建后安装，完全重启微信。
2. 在“增强”或“新功能”打开开关，保存。
3. 分别长按文字、图片、语音、引用消息，重复打开菜单；若另有模块添加项目，测试添加后的菜单。
4. 安全的普通菜单项可自行点击验证原生行为（无需测试删除或转发等有副作用操作）。
5. 关闭保存，再长按消息，确认原生行为不变。
6. 导出包含上述前缀的完整运行日志，并提供菜单截图。

需要从日志确认：菜单模型数量、实际构造数量、挂入数量、真实行容器层级、原始索引与点击签名、V/J/t 类型。运行日志不能替代完整方法的控制流证据；如仍不足，应继续单点诊断或取得定向反编译，不据日志猜测实现。

未执行本地 Gradle 构建。本仓库只有 dev/origin/dev，当前不具备 main/alt-entry 同步条件。未修改动态角标代码。

## 实机证据与诊断减负修订

用户对照测试关闭消息菜单开关重启后角标正常，开启后异常，说明新增开关链路存在干扰。初版四次显示输出975条诊断；显示期间在主线程反射、遍历字段和View树、逐项输出日志，是本轮明确移除的开销，但尚不能认定是唯一根因。

实机确认 eu5.l0 是点击监听对象，不是 View；构造为 eu5.l0(eu5.s0,int)，字段d为索引、e为菜单对象，点击为onClick(View)。首次测试构造索引0～16的17个监听，三个行容器各挂入5个子项。J为onShow()，t为a(View,int,MenuItem)，V在样本中为空。createdViews=0 是初版计数对象错误，不能用于判断图标创建失败。

减负版删除所有菜单对象字段遍历、View树扫描、逐项日志、项目映射、点击观察Hook和下一帧扫描。只保留已验证显示入口与精确监听构造签名，构造回调只累计当前线程会话计数。每次显示最多一条不可变摘要，后台单线程输出，最多一个待处理任务，繁忙时丢弃额外摘要；不把菜单或View对象传递到后台，不积压队列。关闭开关不建立诊断会话，销毁时卸载Hook、清理线程局部状态、关闭执行器。

摘要字段：session、listenerCount、nativeCallMs、nativeFailed、mode=lightweight、nativeUnmodified=true、capacityExpansion=NOT_IMPLEMENTED。监听数量不是图标数量。安装日志为mode=lightweight。最终6×5仍未实现。

测试请分两步：开启保存重启后先不打开消息菜单，观察列表角标；再长按消息并返回列表观察角标。与关闭开关重启的结果对照，回传日志和截图。本次不更改动态角标实现，复测前不声称干扰彻底消除。

Hc.apk 原附件路径当前不存在，未成功读取或逆向，需要重新提供文件。拿到后先检查ZIP清单与DEX字符串，再定向分析候选类，不运行Operit内的全量JADX/apktool。缺少项目View创建和点击控制流证据时，不用运行日志猜测替换实现。


## 关闭安装隔离修订

最新日志在15:02:45保存关闭，15:02:57重启后仍出现stage=install，确认旧版关闭只控制回调，没有阻止Hook安装。但不能由此认定Hook安装就是角标异常唯一根因。

本修订在onFeatureInstall入口判断关闭，直接返回，不创建runtime、不调度安装、不订阅DexReady；安装函数另加关闭防护，避免等待期间关闭仍安装。开关变更均需完全重启微信；已装Hook在本进程内不随开关自动卸载。关闭重启日志应出现stage=installSkipped reason=disabled runtimeCreated=false hooks=0（如果框架提前跳过安装，则可能仅有框架跳过日志），不应出现stage=install mode=lightweight。

本次未修改动态角标源码。该版本只建立关闭状态的完整隔离；开启状态异常尚未修复，6×5仍未实现。优先用关闭保存后完全重启验证：如果仍异常，则消息菜单运行时不是必要条件，应检查角标启动映射和构建产物，不继续凭猜测更改菜单Hook。
