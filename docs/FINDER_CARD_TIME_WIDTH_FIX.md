# 视频号卡片时间宽度修复

本次基线：`120617f641a5c44a40e29f483550975dbc1f4bb7`，分支 `dev`。原先按要求保留本地；随后用户授权与右划复读弹窗首帧修复全部统一提交、推送。

## 原因与证据

微信 8.0.78 解包目录 `/sdcard/Download/wechat8078_decoded` 中，`smali_classes6/com/tencent/mm/ui/chatting/viewitems/p7.smali` 的 `a(Context)` 按窗口短边的 3/8 计算卡片像素宽度，`b(View, boolean)` 将其写入字段 `r` 指向的 `id/bkg` 的布局参数。接收布局为 `ux/uy`，发送布局为 `wh/wi`，分别由 `r7/t7` 使用。`res/layout/bkg.xml` 是同名的另一种资源，不作为视频号卡片依据。

模块旧逻辑在发送侧创建宽度为 WRAP_CONTENT 的列，时间文字可参与撑宽；接收侧把时间直接放在包含昵称的垂直容器中，时间区域也没有保持视频号卡片宽度边界。长文案或显示设置变化会放大这个测量问题。源码证据支持修复容器宽度约束，尚无实机证据证明某一具体 DPI 设置为触发条件。

## 修改

- 收发两侧统一使用视频号专属列，保持原生卡片位置、外侧边距、重心及兄弟顺序。
- 每次测量优先读取宿主卡片的正数布局宽度，回退到有效的已测宽度；以该像素宽度测量时间列，长文案在列内换行，列高度保持内容自适应。
- 重复绑定复用同一列；移除时间后恢复原生槽位及当前卡片尺寸。
- 不增加全局监听、异步任务或滚动扫描。

## 验证范围

执行 `python scripts/test_finder_card_time.py`：提取生产 resolver 并使用完整生产容器进行隔离 JVM 布局夹具检查，再用 Android 36 SDK 定向编译二者。夹具覆盖收发方向、5种卡片像素宽度与4种文字期望宽度、宽度动态变化、隐藏/脱离/空字段、5000次重复绑定、50次清理恢复、原槽位和边距保存。夹具的测量模型只用于边界回归，不代表 Android 实际 TextView 排版。

最终执行结果以本次检查日志为准。不运行 Gradle、不构建 APK。尚未完成新版实机验收；仍需在微信中确认收发视频号长时间文案、显示大小/字体设置变化、滚动复用及关闭功能后的原生布局恢复。其它微信版本的内部结构没有在本次核实。


## 后续边缘对齐修复（与动态撤回修复统一提交）

用户新版截图显示发送侧时间仍偏左。核查发现通用时间左右边距默认 64dp；视频号改成卡片等宽列后仍继承这个整行边距，导致二次内缩。通用时间控件还有左右各 4dp 内边距。此前宽度测试没有覆盖这个对齐契约，不能视为实机效果通过。

新增视频号专属时间布局参数：MATCH_PARENT 宽度、零水平外边距与内边距，按收发设置 END/START 文字对齐；保留文字上下内边距及卡片下方 2dp 间隔。头像隐藏时也不继承旧边距，不再调度无需执行的外部对齐监听。其它消息类型保持原配置。

本轮附件日志记录了消息时间功能已安装，以及绑定前状态读取空引用异常；堆栈经过混淆，未证明与水平偏移有关，本次没有将其认定为根因或宣称解决。

本轮 `scripts/test_finder_card_time.py` 收发回归与 Android 36 SDK 定向编译通过，增加对完整宽度、零水平边距/内边距、收发文字方向的检查，保留5种卡片宽度、4种文案宽度及复用恢复检查。未运行 Gradle、未构建 APK；未做新版实机验收。不提交、不推送。

## 视频号时间单行显示调整

用户实机确认左右位置正确，但要求长时间文案不换行。此前按卡片宽度约束文字与多行策略直接导致截图换行。本次将卡片宽度与时间宽度分开：时间预先按聊天行扣除左右配置边距后的可用宽度测量，列取卡片和时间宽度的较大值；卡片保持原生宽度并与时间共同按收发方向靠边。时间固定单行，超过整行可用宽度时尾部省略，避免扩大消息行。保留文字字号、上下边距和复用恢复。未新增监听、后台任务或滚动扫描；每次容器测量额外进行一次时间测量。

专项夹具覆盖5种原生卡片宽度与4种文案宽度，验证卡片宽度不变、时间单行、行宽上限、收发重心和恢复；生产容器及定位方法 SDK 编译通过。新版实机单行和卡片位置仍待确认，未执行 Gradle/APK 构建。本项先保留本地修改。
