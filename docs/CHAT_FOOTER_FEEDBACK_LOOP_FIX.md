## 原因

此前把列表 padding 稳定作为整个输入区结构成功条件。原生列表仍有布局请求时，apply返回false；有限重试耗尽后恢复层级、边距、padding。恢复本身又产生布局事件，仍活跃的global/layout回调重启应用。attempts未阻止后续回调，所谓三次上限只限制一轮，未限制整个失败实例。循环产生重复拆装、布局和绘制取消，输入区恢复到原生屏外锚点，符合消失和卡顿表现。

## 修正

- 输入区结构成功与列表布局稳定解耦：挂载、测量和边距合法即成功，不因列表pending回滚结构。
- 首次结构成功后，用独立settlePasses最多三次检查列表避让，只调用padding方法，不重新执行apply/reparent/restore。超限允许绘制，不持续阻止整页显示；因此不能承诺极端布局时序下完全没有消息跳动。
- scheduleFooterApply默认不请求额外布局；仅真实层级、边距和padding变化请求原生布局。
- 真正结构失败耗尽重试后标记failed，移除global监听，并在所有后续调度入口拒绝重启该失败实例。detach/重新创建实例后重新初始化。
- 不新增滚动监听、持续轮询、数据库读取、主动消息滚动或逐帧全树扫描。保留限频诊断；新增footer-settled报告有限等待结果。
